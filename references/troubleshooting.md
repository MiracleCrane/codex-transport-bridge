# 桥接排障与已踩过的坑

只查当前问题涉及的边界。安装与配置所有权见 [安装说明](installation.md)，套件集成见 [组件契约](../docs/component-contract.md)。

| 现象 | 先核对 |
| --- | --- |
| 重启后 `10061`、反复连接被拒绝 | 实际 URL 的端口、监听进程、真实快捷方式的整条包装链。曾经只改了回滚 `.lnk`，活动入口仍拉起旧版。 |
| 端口健康但聊天仍走旧入口 | 已加载会话可能保留原配置；关联该聊天 ID 的实际连接，不能只看新文件。 |
| “正在思考”很久 | UI 是活动提示，“已处理 N 秒”也是本轮计时，并非服务端开始推理的回执。查首个协议事件、reasoning item、正文 delta 和重试。 |
| 大量输入、缓存命中为 0，途中又 steering | 冷请求处理和中断/下一次采样可能拉长等待；不能与高缓存的小问答直接对照，也不能只凭 UI 判定失联。 |
| WebSocket 在 `response.completed` 前关闭 | 区分上游先关闭与调用方取消；收到关闭后的转发时延和此前静默原因分开判断。 |
| HTTP 200 后出现 `error decoding response body` | 对齐 `http_response_error` 的错误码、完整性标志、最后收包间隔和缓冲字节。旧版会直接销毁下行并丢尾；1.4.0 起保留已收到的尾部字节，缺失完成事件仍视为失败；对应夹具在 tests/http-response-drain.test.mjs 与 tests/native-client-fixture.mjs。 |
| `upstream-liveness-timeout` | 对应连接的匹配 Pong 未在期限内完成；`write_pending` 与 `awaiting_pong` 分别表示探测写入未完成、写完后未收到匹配回应。 |
| `upstream-pong-timeout` | 上传窗口确认未完成。不能用早于该窗口字节发出的心跳 Ping，来确认后面上传的字节。 |
| 上游始终回应 Pong，却仍无模型输出 | 传输仍有响应；桥接不能据此区分后端排队、未缓存输入处理和模型内部异常。不能用固定正文超时强行截断正常推理。 |

## 当前实现边界

- 原生 HTTP 和 WebSocket 都固定转往官方 `chatgpt.com/backend-api/codex/`，保留 TLS 验证及原认证语义。
- WebSocket 分片与确认控制上传进度；小消息和最终尾段也由独立存活探测覆盖。
- 默认存活检查间隔 15 秒、匹配 Pong 期限 25 秒；这是传输探测期限，不是模型推理期限。事件循环、下行排空和关闭握手可能增加实际收尾时间，不把它宣传成严格端到端 SLA。
- 上传与存活探测串行协调。上传必须由位于当前字节窗口之后的 Ping 确认，不能复用更早的心跳确认来清空整个字节额度。
- 失联关闭先给已收到的下行消息有界排空，尤其不能丢掉已经到达的 `response.completed`；调用方取消仍及时退出。
- 1.4.0 同样覆盖 HTTP 响应异常：排空已有字节后关闭原始 socket，保留 HTTP 非正常结束，不补正常 chunked 终止块或模型完成事件。`http_failed` 是传输层结果；若完成事件已送达，实际客户端可能已经成功，仍需关联该聊天状态。
- HTTP 错误日志中的 `lastDataAgoMs`、`downstreamBufferedBytes`、`upstreamLocalPort`、`upstreamComplete` 和 `errorCode` 用于区分上游截断与本地丢尾，不记录正文/认证头。断流后清理下行产生的 close 不再误记为调用方主动取消。
- 桥接不重放已经发送的模型 POST/WS 请求。恢复由 Codex 自己的重试机制处理，不伪造成功事件。

## 调试纪律

只输出时间、错误类别、端口、版本、实例/PID、字节数和事件种类。HTTP 原始头、cookie、token、会话正文、认证文件、完整进程环境和带敏感参数的命令行不能输出或提交。

本地测试使用全新临时目录，测试证书仅通过测试子进程的 `NODE_EXTRA_CA_CERTS` 信任，不修改系统证书库。运行 `Test-Offline.ps1` 时可明确复用匹配版本的依赖目录；普通安装仍按 lockfile 拉取。

一次本地回归不等于该机器真实会话验收；一次正常回复也不证明所有负载更快。用户允许一次轻量模型测试时才做该测试，并按子会话 ID 核对路径，不凭总计数增长判断。用户要求正常使用后，不自行安排定时观察、启动循环压测或降低模型档位。
